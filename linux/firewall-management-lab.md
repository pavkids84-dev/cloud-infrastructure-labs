# Linux Firewall Management Lab

## Objective

Practice Linux firewall administration with firewalld on Rocky Linux.

The goal of this lab is to understand Linux firewall layers, inspect firewalld zones, distinguish runtime and permanent configuration, manage services and ports, associate network interfaces with zones, create a custom zone, and use firewall state as part of network troubleshooting.

## Environment

- OS: Rocky Linux
- Shell: Bash
- Firewall Service: firewalld
- CLI: firewall-cmd
- Init System: systemd
- Privilege: root or sudo-enabled user

## Safety Notice

Firewall changes can immediately interrupt remote access.

Before changing firewall configuration:

```text
Confirm console access
Confirm the active network interface
Confirm the current zone
Confirm existing SSH access
Record the current firewall configuration
```

Do not change the default zone to `trusted` or remove SSH access on a remote system unless an alternate recovery method is available.

Use a disposable virtual machine for experiments that can interrupt connectivity.

## Firewall Overview

A firewall controls network traffic entering or leaving a system.

A simplified Linux network path is:

```text
Network
   |
   v
Network Interface
   |
   v
Linux Firewall
   |
   v
Application / Service
```

A service can be running correctly while remote access still fails because the firewall does not permit the required traffic.

## Linux Firewall Layers

The course introduces:

```text
Netfilter
iptables
nftables
firewalld
```

A useful conceptual model is:

```text
firewall-cmd
      |
      v
firewalld
      |
      v
Firewall Rules
      |
      v
Linux Kernel Packet Filtering
```

Netfilter is the kernel-level packet-filtering framework.

firewalld provides a higher-level management model based on concepts such as zones, services, ports, interfaces, and sources.

## Zone Concept

firewalld uses zones to group firewall policy according to network trust or usage context.

Conceptually:

```text

```

The course demonstrates a runtime assignment using the `work` zone.

General form:


```bash

```

Use only the actual interface identified on the disposable VM.

## Runtime Configuration

A command without `--permanent` modifies the runtime firewall configuration.

Example:

```bash
sudo firewall-cmd --zone=work --add-service=ftp
```

Verify:

```bash
firewall-cmd --zone=work --list-all
```

Conceptually:

```text
Runtime Rule
     |
     v
Current firewalld State
```

A runtime-only rule should not be treated as persistent configuration.

## Permanent Configuration

The course demonstrates:

```bash
sudo firewall-cmd --permanent --zone=work --add-service=ftp
```

Apply the permanent configuration to the running firewall:

```bash
sudo firewall-cmd --reload
```

Verify:

```bash
firewall-cmd --zone=work --list-all
```

The relationship is:

```text
Permanent Configuration
        |
        v
firewall-cmd --reload
        |
        v
Runtime Configuration
```

## Runtime and Permanent Configuration

This distinction is critical.

```text
Runtime
----------------------------
Current firewall state

Example:
firewall-cmd --add-service=http


Permanent
----------------------------
Configuration intended to persist

Example:
firewall-cmd --permanent --add-service=http
```

A runtime-only modification can disappear when the firewall configuration is reloaded.

## Service and Port Rules

The two rule styles should be distinguished.

```text
Service Rule
→ Named firewall service

Example:
http


Port Rule
→ Explicit port and protocol

Example:
2888/tcp
```

Choose the rule style intentionally rather than adding both without understanding the requirement.

## Change the Default Zone

The course introduces:

```bash

```

Before changing the default zone, inspect:

```bash

```

Do not change it on a remote production system without understanding the current interface-to-zone assignments.

## Trusted Zone Safety

The course demonstrates temporarily changing the default zone to:

```text
trusted
```

for testing and then returning to:

```text
public
```

The `trusted` zone should not be used as a generic troubleshooting shortcut.

A safer troubleshooting approach is:

```text
Inspect active zone
        |
        v
Inspect services and ports
        |
        v
Identify the exact missing rule
        |
        v
Add only the required access
        |
        v
Retest connectivity
```

Do not switch the lab VM to `trusted` unless the exercise specifically requires it and the network impact is understood.

## Custom Zone Concept

The course demonstrates defining a custom zone using an XML file under:

```text

```

Course example:

```text
/etc/firewalld/zones/sec.xml
```

with content similar to:

```xml
<?xml version="1.0" encoding="utf-8"?>
<zone>
  <short>security-congress</short>
  <description>For use at the security congress.</description>
  <service name="ssh"/>
</zone>
```

This demonstrates that zones can define their own services and descriptive information.

## Firewall Troubleshooting Model

When a remote application cannot be reached, do not assume the firewall is the cause.

Use a layered troubleshooting process.

```text
Remote Connection Failure
          |
          v
Is the application running?
          |
          v
Is the expected port listening?
          |
          v
Is the correct network interface active?
          |
          v
Which firewalld zone applies?
          |
          v
Is the required service or port allowed?
          |
          v
Retest the remote connection
```

## Step 1: Inspect the Service

For a systemd-managed service:

```bash
systemctl status SERVICE
```

Confirm that the application is actually running before changing firewall rules.

## Step 2: Inspect Listening Ports

Use an available socket-inspection command in the current environment to confirm that the expected application port is listening.

Do not open a firewall port for a service that is not listening unless the test intentionally requires it.

## Step 3: Inspect Firewall State

```bash
systemctl status firewalld
```

Then:

```bash
firewall-cmd --get-default-zone
```

and:

```bash
firewall-cmd --list-all
```

Identify the currently applied firewall policy.

## Step 4: Identify the Missing Rule

Check service permission:

```bash
firewall-cmd --list-services
```

Check explicit ports:

```bash
firewall-cmd --list-ports
```

Do not add unrelated rules.

## Step 5: Apply a Controlled Change

For a temporary test, add only the required service or port.

Example:

```bash
sudo firewall-cmd --add-port=2888/tcp
```

Verify:

```bash
firewall-cmd --query-port=2888/tcp
```

Then retest the network connection.

## Step 6: Decide Whether the Rule Should Persist

If the access is required after reboot or firewall reload, configure the corresponding permanent rule.

Example:

```bash
sudo firewall-cmd --permanent --add-port=2888/tcp
```

Then:

```bash
sudo firewall-cmd --reload
```

Verify again:

```bash
firewall-cmd --list-ports
```

## Runtime vs Persistent Troubleshooting

A common configuration problem is:

```text
Port Works Now
      |
      v
Firewall Reload or Restart
      |
      v
Port Is Blocked Again
```

Investigate whether the original rule existed only in the runtime configuration.

The underlying concept is:

```text
Runtime State
≠
Persistent Configuration
```

This pattern also appears elsewhere in Linux administration.

```text
systemctl start
≠
systemctl enable

sysctl -w
≠
persistent sysctl configuration

runtime firewall rule
≠
permanent firewall rule
```

## What I Learned

- A running service can still be unreachable because network access is controlled at another layer.
- Linux packet filtering and firewalld should be treated as different parts of the firewall stack.
- firewalld organizes policy using zones.
- Interfaces and source networks can be associated with firewall zones.
- `firewall-cmd` is the primary CLI used in this lab.
- Named services and explicit ports provide different methods of permitting traffic.
- Runtime firewall state and permanent firewall configuration are separate.
- A permanent configuration change must be applied to the running firewall before it affects runtime behavior.
- Firewall rules should be verified after every change.
- Switching to a fully trusted firewall policy is not a substitute for identifying the required rule.
- Firewall troubleshooting should first confirm the application and listening port before changing network policy.
- Infrastructure troubleshooting is more reliable when application, service, firewall, and network layers are investigated independently.
